# Deploying SteadN to steadn.com

Five files here, plus two SQL files for later. Roughly an hour to a live site.

---

## What changed from the prototype, and why it had to

The artifact version leans on two things that only exist inside Claude's sandbox. Both fail **silently** on a real domain, which is the dangerous kind of failure.

| | prototype | this build |
|---|---|---|
| Saving | `window.storage` (sandbox only) | localStorage, via a shim with the same shape |
| Advisor | calls `api.anthropic.com` directly | calls `/api/ask`, which holds the key server side |

The shim means **the app code is unchanged.** Only the mechanism underneath differs, so the prototype and the live site stay in sync.

The API change is not optional. Anything in your client bundle is public. A key in the front end is a key you have given away, and it will be found by a scraper within days.

## Step 1 — put the site up, without installing anything

You do not need a terminal, Node, or Git on your machine. All of this happens in a browser.

### 1a. Make a GitHub repository

1. Go to **github.com/new**
2. Name it `steadn`. Set it **Private**. Do not tick "add a README".
3. Click **Create repository**

### 1b. Upload these files

On the empty repo page, click **uploading an existing file**.

Drag in **the contents of this folder**, not the folder itself:

```
index.html
package.json
vercel.json
manifest.webmanifest
icon.svg
sw.js
api/          <- drag this folder in too, the structure matters
schema.sql
admin.sql
README.md
```

Dragging the `api` folder keeps `api/ask.js` where Vercel expects it. If your browser will not drag a folder, use **Add file → Create new file**, type `api/ask.js` as the name (the slash creates the folder), and paste the contents in.

Click **Commit changes**.

### 1c. Point Vercel at it

1. **vercel.com/new**
2. **Import Git Repository**, authorise GitHub if it asks, pick `steadn`
3. Framework Preset: **Other**. Leave build and output settings empty. There is no build step.
4. **Deploy**

You will get a `something.vercel.app` URL in about a minute.

### 1d. Attach your domain

**Project → Settings → Domains → Add → `steadn.com`.** Vercel tells you which DNS records or nameservers to set at your registrar. Anywhere from a few minutes to a few hours to propagate.

### From then on

Editing a file on github.com and committing it redeploys the site automatically. That is your whole release process, and it means you never need a local setup at all.

## Step 2 — give the advisor a key

**Settings → Environment Variables**

| name | value | scope |
|---|---|---|
| `ANTHROPIC_API_KEY` | your key from console.anthropic.com | Production, Preview |

Redeploy after adding it. Environment variables are only read at build and runtime, so an existing deployment will not pick it up.

Check it worked: open the site, go to **Ask**, ask anything. If you get "Advisor is unreachable", the key is missing or wrong — look at **Vercel → Logs**, not the browser console, because the error is deliberately vague on the client side.

## Step 3 — confirm it installs and runs offline

On your phone, open steadn.com, then **Share → Add to Home Screen**. It should open full screen with no browser chrome.

Then put the phone in airplane mode and open it again. The almanac, your garden, the canning times, and the whole library should work. Only **Ask** should fail, and it should say so rather than hanging.

If it does not work offline, the service worker did not register. Check **Application → Service Workers** in desktop dev tools.

## The files

```
index.html            the whole app, 476 KB, no external requests
api/ask.js            serverless proxy, holds the key
package.json          tells Vercel this is a module, and which Node
sw.js                 service worker, makes it work with no signal
manifest.webmanifest  makes it installable
icon.svg
vercel.json           cache and security headers
schema.sql            Supabase tables and row level security, for later
admin.sql             staff roles, audit and analytics, for later
```

`package.json` looks trivial but is not optional. `api/ask.js` uses `export default`, which is ES module syntax, and Vercel's Node runtime reads a plain `.js` file as CommonJS unless `"type": "module"` says otherwise. Without it the advisor throws on the first request.

`index.html` is regenerated by `node deploy.js` from the prototype. Edit the source modules and rebuild, never edit `index.html` directly.

## What this does NOT do yet

Be clear eyed about this before you show anyone.

**Storage is per device until you do step 4.** Someone who plans on a laptop and picks on a phone has two unrelated gardens until accounts are switched on.

**The AI quota is not enforced.** The thermometer is a courtesy display. The server does not check it, so nothing stops someone from asking a thousand questions and spending your money. `api/ask.js` has a crude per-IP limit that stops a runaway loop, and that is all.

**Nobody can pay you.** No Stripe.

All four have the same fix.

## Step 4 — accounts and syncing

This is what makes a garden follow someone from the laptop to the phone.

### 4a. Create the project

1. **supabase.com** &rarr; New project. Any region near you.
2. **SQL Editor** &rarr; paste `auth.sql` &rarr; **Run**
3. **Authentication &rarr; Providers &rarr; Email**: turn on **Enable email provider** and **Enable email confirmations**, which is what sends the magic link
4. **Authentication &rarr; URL Configuration**: set **Site URL** to `https://steadn.com` and add `https://steadn.com` to **Redirect URLs**. The link will not come back to your site without this.
5. **Project Settings &rarr; API**: copy the **Project URL** and the **anon public** key

### 4b. Put them in the app

Open `index.html` on GitHub, click the pencil, and find this near the top of the script:

```js
const SUPA = {
  url:  '',          // https://xxxxxxxx.supabase.co
  anon: '',          // the anon public key
};
```

Fill both in and commit. Vercel redeploys.

**The anon key belongs in the browser.** It grants nothing by itself: the policies in `auth.sql` decide what any request can reach. The **service_role** key is the dangerous one, and it must never appear in this file or anywhere else a browser can see.

### 4c. Check it

1. Open steadn.com. The sign in screen should no longer say "not switched on yet".
2. Enter your email, click the link when it arrives.
3. Build a garden.
4. Open steadn.com **on your phone**, sign in with the same email. Your beds should be there.

The chip in the header tells you where things stand: **Synced** means it reached your account, **This device** means it saved locally and will go up when the connection returns, **Two copies** means another device saved a different version.

### What happens offline

Local always saves first and never waits on the network, so the app is fully usable in a dead zone. The account copy catches up when signal returns.

If two devices edit while one is offline, the second one to reach the server is refused rather than allowed to flatten the other, and the chip shows **Two copies**. That is deliberate: silently losing a season of harvest records would be far worse than asking.

## Step 5 — the rest, when you want it

`schema.sql` and `admin.sql` are written for Supabase.

1. Create a project at supabase.com
2. **SQL Editor** → paste `schema.sql` → run
3. Same again with `admin.sql`
4. **Authentication → Providers → Email**, turn on magic links, set the redirect to `https://steadn.com`
5. Add to Vercel: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`

**The anon key is safe in the browser. The `service_role` key is not, ever.** The anon key does nothing on its own because row level security decides what it can reach. The service role key bypasses every policy in both SQL files. If it lands in your client bundle, every customer's data is readable by anyone.

Then, in this order:

1. Record each advisor call in `ai_usage` and refuse in `api/ask.js` when the plan quota is spent. Until this exists the thermometer is a courtesy and nothing caps your spend.
2. Stripe, with a webhook writing to `subscriptions`
3. Move from the single state blob in `auth.sql` to the normalised tables in `schema.sql`, which is what sharing and analytics need

Before you trust the admin side, run the verification block at the bottom of `admin.sql`. Create a staff row for yourself, then a second ordinary account, and confirm every admin view comes back empty from the ordinary one. If it does not, the policy is not doing what you think.

## Costs at a small scale

| | |
|---|---|
| Vercel Hobby | free, fine until you have real traffic |
| Supabase free tier | 500 MB, enough for a few thousand steads |
| Anthropic | per question, roughly 2 to 5 cents with search |
| Domain | you already have it |

So the only line that moves with usage is the advisor, which is why it is the thing that is metered and why enforcement belongs on the server rather than in the thermometer.

---

## One suggestion about order

The offline shell now works, which is your actual differentiator. Nobody else in this space has it.

I would put the app in front of five real homesteaders **before** building auth and billing. Per-device storage is a genuine limitation, but it is survivable for a first look, and what you learn from watching somebody try to lay out their actual garden will change what you build next more than any amount of backend will.
